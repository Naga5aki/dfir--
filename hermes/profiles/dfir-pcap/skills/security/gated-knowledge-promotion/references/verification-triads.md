# Verification triads for a promotion round

Three layers, in this order: validator → failure probes → fresh-context smoke test. Each layer's result is a JSON artifact the report cites.

## 1. Path-injectable validator

- Every root is a CLI argument (`--store --staging --backup --round --base-manifest --out`), plus `--lite` (skip heavy subprocess checks) and `--allow-pending`. Probes depend on this: they run the same validator against a temp sandbox and a reduced baseline.
- Check catalog that has proven sufficient (19 checks): anchors unchanged; upstream validator in strict + accounted mode; pinned/restored file state; backup completeness vs its manifest; staging↔store bytewise equality; numbering unique + continuous (`nums == list(range(1, len(nums)+1))`); store structure (file set, section count, entry count); label legality; disposition completeness (all required fields non-empty, disposition in the allowed set); conflict register clean or fully registered; leak verdict + live NEW-content re-scan; forbidden artifacts absent (walk for forbidden NAME patterns); protected stores zero-modified vs freeze manifest (subsets by purpose prefix); external tool config zero-modified (hash from freeze manifest + mtime before round start + registration entry present); disk read-back vs apply record; smoke test passed; manifest consistency; probes all behaved.
- Result shape: `rec(id, name, ok, detail, pending=False)` per check; JSON with `checks[], pass, fail, exit_code`; big evidence (counts, hash prefixes) into `detail`; `exit 1 if any(not ok and not pending)`.
- Label legality is a two-tier check: (a) line-end parenthetical groups whose text contains a status keyword must be composed only of whitelisted fragments — an unknown fragment fails; (b) a forbidden-marker regex (`Verified`, `Partially Validated`, `100%`, "all scenarios verified", "no limit needed") catches Source-Only→Verified upgrades and scope widening. Separately, require every limited/partial item's body to carry an explicit `限制：...` line and fail the item if it is missing.
- Keep the live leak re-scan inside the validator: re-run the NEW-content scan against the injected store so probe sandboxes can watch it trip.

## 2. Failure probes (sandbox matrix)

- Use one FRESH sandbox per probe under the task-approved scratch or test root, not an implicit system-temp location: copy store + staging + backup + pinned files + a reduced baseline manifest; run the validator with every path pointed at the sandbox (`--lite --allow-pending`). Never mutate the real store.
- Mutation set that must each trip its own check: duplicate numbering; forbidden token injection; controlled-hash injection; Source-Only re-labelled Verified; scope widening (strip a limit line); staging↔store mismatch; required new file missing; backup file missing; pinned file modified; protected store modified. Final probe: unmutated sandbox exits 0.
- Record per probe `{id, name, target_check, rc, failed_checks, behaved}` plus `all_behaved`; a probe "behaves" when its target check is among the failures (rc=0 for the clean one). Side-effect failures (e.g. equality checks after an in-place mutation) are expected and fine.
- Reduced baselines in probes (small manifest, narrowed scan roots) are legitimate — the check logic is what is under test — but say so in the probe artifact.

## 3. Fresh-context smoke test

- Dispatch a new isolated session whose ONLY inputs are the promoted store files (absolute paths) + the question list; explicitly forbid reading sources, staging, cards, and reports.
- Mix ~20 substantive questions spanning every promoted section with 2 control questions whose answers are NOT in the store. Controls must return "not covered"; an answered control proves fabrication and invalidates the rest.
- Score exactly the numbers usually asked for: retrieval success rate (valid, existing locators), rule hit rate, error extensions, unverified-range false positives. Bar: zero on the last two.
- Re-derive the score: grep the store for the key phrases each answer claims, check that cited locators exist, and only then compute rates. A styled answer set with plausible citations is cheap to fake and cheap to verify.

## 4. Accounting mode for a legacy validator

Recipe (also a SKILL.md pitfall): strict run → parse fails → recompute the freeze-mismatch set locally (validator details truncate to the first few paths) → require it to equal exactly the authorized changed files → build (a) a full-workspace account manifest and (b) an updated freeze manifest whose rows for the authorized files carry post-change hashes → the accounted run must be fully green. Build the account manifest AFTER all run outputs that should be registered exist, and BEFORE the accounted run writes its own result, so the result file never strands as "unregistered".

## 5. Reconstruction check (in-place patch rounds)

When the round applies recorded edits in place, the strongest verdict is reconstruction: take the pre-change backup, replay the FULL recorded edit list in order (in memory; normalize line endings only if the copy crossed a layer that rewrote them), and byte-compare the result to the live store per file (`all_match=True`). It catches under- and over-application in one pass, and it is the authoritative verdict when the apply tool's own self-check false-fails — a check demanding "the old anchor vanished" cannot hold for append-type edits (new = old + expansion), which are a legitimate minimal-modification shape. Archive the reconstruction JSON, cite it in the report, and explain any nonzero tool exit as the check's blind spot rather than a content defect.

## 6. Runtime-drift attribution (strict "zero-write" failures you did not cause)

When the final strict check flags files nobody in the round wrote — skill-tree files whose mtimes cluster seconds apart, plus a `.locks/<hash>.lock` and the usage sidecar — suspect the host runtime first: the skill curator patches managed skills as an auto-lesson pass, tagging every mutation with the session it learned from.

1. Diff the formal state against the round's baseline for the exact changed/added/removed set; the mtime cluster is itself evidence (one pass touches several files within seconds; `ts` in the ledger is UTC — convert before comparing with local file times).
2. Read the tail of `skills/.curator_ledger.jsonl`, filter by `evidence.session_id == <this session>`; fields: `id, ts, actor (curator|agent), action (patch|write_file), skill, before[]/after[] sha256`. The file diff must match the entries 1:1 (each intermediate patch counts separately), and chain-final `after` hashes must equal the files on disk.
3. Exonerate or convict your own workers independently: grep the delegation transcripts for `skill_manage`, `curator`, and the drifted filenames. Zero transcript hits + ledger hits = runtime write, not a reviewer violation.
4. Recoverability: `.curator_backups/blobs/` is content-addressed (filename IS the sha256; verify by re-hashing). Check both `before` and `after` blobs per entry, and build the pre→current diff from the `before` blob vs the live file. The documented owner-side undo is `hermes curator rollback <entry-id>` — never exercise it on the owner's behalf; a session-triggered pass may leave `.curator_state` counters and `logs/` untouched, so use the ledger as the record, not those.
5. File the accounting artifact: per drifted file baseline/current size+sha256+mtime, the ledger entries verbatim, the blob-verification table, exclusion evidence, and the diff path; state the split verdict (strict not met / drift attributed to the host runtime, session and source writes excluded) and say the frozen report/sidecar/manifest were intentionally left unedited — the accounting artifact supersedes their stale "only exception" sentences.
6. A runtime pass since the baseline invalidates the before-state for the next phase — re-take the baseline before anything builds on it.

## 7. Structured CLI and service-probe regressions

Use this recipe when the promoted validator wraps a CLI, MCP session, or other business-operation probe. Keep transport success, functional success and simulated contract checks separate.

1. **Define the success predicate before constructing positive controls.** Require the response structure and concrete business data that establish the requested operation. Treat keyword presence, nonempty text, tool discovery and an error-free transport envelope as observations, not functional proof. If no reliable success schema is established, retain the contract's unverified outcome rather than inventing a success schema or a natural-language error blacklist. Add a negative response that contains every expected marker while explicitly describing failure; it must never become functional success. Preserve strict missing-field, wrong-type and contradictory-data failures.
2. **Separate metadata from operation-result envelopes.** Validate inventory names/counts independently of response error flags. Test legitimate schema properties named `error`, `isError`, `is_error`, `exception` or `traceback` in required and unrelated tool descriptors; declarations are not runtime errors. Exclude only documented metadata positions from error scanning, while keeping actual root, business-result and raw-envelope errors effective. Do not globally ignore every recursively encountered key with a metadata-like name.
3. **Prove each failure test reaches its intended branch.** Mock the external connector/probe before enabling an execution scope or supplying permission flags. Run the smallest regression first, assert the exact expected outcome and exit code, and assert the injected result was consumed. Keep separate tests for default-offline behavior and denied permissions. A nonzero static/unverified result is not evidence that an injected business error was checked.
4. **Exercise reporting paths outside the business-call try/except.** Cover invalid choice values, failed numeric conversion, unknown/missing arguments, and output-write exceptions. Require one safe structured stdout report with an exit code matching its outcome; do not echo arbitrary argument values, exception messages, paths or raw credentials. Define and test any human-readable help exception explicitly. Label an injected filesystem exception as injected coverage, not as proof of a real malformed-path reproduction.
5. **Run the actual entrypoints after the tight loop is green.** Capture subprocess command, working directory, actual exit, stdout/stderr, provenance and scope. Select the parser from the declared invocation contract, not from whether JSON decoding happens to succeed: validate a standalone human-readable help invocation separately, and require every other row to parse as one JSON document. Recompute JSON-row and help-row counts separately and require their sum to equal the enumerated matrix; assert expected exit = process exit = report exit for every JSON row, and the declared process exit and output shape for help. Assert that fixture runs never claim real service or functional verification; retain a separate real-service gate. Record the exact source/test hashes used by each execution, not only the final source hashes.
6. **Give each evidence run an immutable identity.** Keep run/version identifiers distinct from per-case loop labels, construct the intended output path from the run identifier, and verify that exact path after execution. Use a fresh fixture/output namespace for reruns so exclusive-create evidence writers preserve history. Budget subprocesses from a recent targeted run on the current machine, not a worker's historical duration; give the outer runner enough time for the cumulative inner budgets plus copying, cleanup and evidence writes, or split the battery into checkpointed commands. On timeout, preserve the runner exit and last durable checkpoint, confirm whether owned processes remain, and inventory any partial sandbox before retrying; a harness timeout alone is neither a product failure nor a completed test. If the writer or harness changes, retain the earlier artifact with its limitation and rerun the complete affected battery; do not merely rename an old result and call it a new run.
7. **Repeat independent review against the current staged revision.** Provide current source hashes and the regression artifacts, preserving earlier findings and manifests as history. A green suite does not close a counterexample by itself. Keep unresolved resource limits, shutdown behavior and real-service coverage explicitly scoped; do not turn untested mitigations into validated procedures.
8. **Prove gate ORDER with spies on the exact stdlib call, not just the denial outcome.** For a pre-read path gate, patch `Path.open` and require zero opens plus the JSON denial reason and empty stderr on every denial case; for a lexical-layer gate, patch `Path.resolve` to raise and count calls — zero resolves proves no filesystem resolution was attempted. Decoys must exist on disk with would-be-valid content so the denial — not a missing file or a schema failure — is the only rejection reason; pair every negative with positive controls (approved inputs and legitimate lookalike names still pass the same gate) to bound over-blocking.

## 8. Application gate and isolated rollback rehearsal (staged-batch installs)

Rounds that build under a staging tree and then install files into live targets add one more layer on top of §5's reconstruction check. For an isolated regression or rollback tree, first inspect how the legacy tests locate their root, then reproduce that layout using byte-identical approved files. Enumerate the approved navigation and evidence-reference targets required by those tests, record any additions to the baseline copy set with their reasons and hashes, and reject prohibited targets rather than copying an entire evidence or dependency tree. The copy set must cover every path the round's checks RESOLVE — candidate-entry `evidence_ref`-style targets included, since validator, report-only checkers and tests all resolve them against the layout root; one absent referenced file bursts across all three layers (validator violations + checker findings + suite failures, all the same root). Classify a burst grouped on one path that exists in live as a rehearsal-composition gap: fix the copy manifest, never the candidate. Do not substitute stubs for referenced files or introduce a staging root marker that redirects legacy root discovery; either can make an otherwise valid implementation fail only in the harness. Run the unchanged legacy suite before overlaying only the exact publication set, then run the combined suite. Keep copy-layout failures separate from implementation failures and retain both the failed attempt and the corrected-layout rerun. When the batch ships its own replica, verify it per file class before trusting it — baseline members byte-equal to live, overlay members byte-equal to the staged candidates, extra support files byte-equal to their recorded sources — then run the suite on your own copy, keeping the shipped replica byte-frozen as evidence. Run the application steps in this order:

1. **Pre-apply gate artifact, before any live write.** Re-hash every staged source against the review-frozen record; byte-check each live target against its backup and freeze manifest (zero drift); verify the absence of every path the batch will CREATE; for every live file the batch will REPLACE that the freeze backup set does not cover (files created since the freeze), take a pre-apply snapshot into a separate backup dir and record its hash; cite the reviewers' report hashes and verdicts. Any failure ⇒ stop, zero writes; end the gate with one verdict string (pass / FAIL_STOP).
2. **Apply + read-back.** Copy bytes; per file assert recorded == staged-before-copy == live-after-copy in one record; write the apply record in the shape the round's other records already use (`installed[]` with path+sha256+matches_stage, command, cwd, result, limits) and, when the change alters a consumer-visible contract (output shape / exit codes), add an explicit consumer note — what changed and what consumers must not infer.
3. **Post-apply live verification, captured not transcribed.** Re-run the promoted suite at the live root plus the neighbouring regression suite, capturing the output programmatically into the record instead of transcribing earlier terminal text. Account skips separately: name each skipped test and rerun it in the layout that lets it run — 'skipped' is accounted, not waived. Re-run the report-only checkers (doctor-style) and require parity with the pre-round known set — identical finding count and classes, zero findings naming round-added paths — in both the rehearsal and at live; a changed count or a new class is a stop, and each run's output is its own artifact.
4. **Isolated rollback rehearsal (never called a live rollback).** In a scratch copy: build the pre-apply state from backups + snapshots; simulate the apply and byte-match the sandbox against the live install, with the pre-suite snapshot comparison asserting the overlay changed exactly the intended set (replaced ∪ created) — no collateral writes; exercise the promoted command in the copy (a byte-correct install is not a wired entrypoint); execute the recorded rollback steps (restore modified, restore snapshots, delete created); verify every restored hash equals the gate's pre-apply records, comparing through ONE exclusion predicate shared by both snapshots for the paths the rehearsal itself creates (test-owned `.tmp`, `__pycache__`, the disposable indexes exercised entrypoints write inside the copy — without it byte-identity false-fails on rehearsal-born artifacts; keep the differing keys in the check detail); then replay the apply once more and byte-match live. Archive all four steps with an `all_pass` verdict.
5. **State the delta and the carried items.** The applied record names the delta vs the freeze manifest (modified / created / replaced), notes that the manifest itself stays the pre-round baseline, and carries forward declared non-blockers so they cannot silently disappear; it also supersedes any earlier stage record's "not published" flag. Applied files stay byte-identical to the reviewed revision — even a reviewer's "fix it along the way" suggestion becomes a carried item for a later authorized round with the deferral recorded; a post-review edit would invalidate the review hashes this record cites. Name runtime-derived artifacts as well: post-apply verification at the live root legitimately creates disposable indexes/caches (documented default paths, test-owned `.tmp` sandboxes) — list them with their deletability so a later zero-new-files audit classifies instead of flagging them as unauthorized additions.

## 9. Frozen-input acceptance for search/retrieval baselines

When a round builds a search/retrieval engine (or swaps its backend) whose acceptance is a query battery, the inputs are pre-registered, not chosen while looking at results:

- **Pre-register before the engine exists.** Freeze the query set, the human-read gold refs (never engine-derived) and the pass criteria (top-k, minimum hit count, per-negative-control expected outcome) into one versioned input file with a sha256 lock; every later gate re-verifies the lock, and both reviewer roles check that neither the set nor the thresholds were edited to fit results. Engine-side tuning is legitimate; set-side tuning never is.
- **No query knowledge inside the engine.** Hits must come from general matching logic; reviewers grep for query-string literals and answer mappings. Returning text that is not literally present in the sources is a release blocker at any score.
- **Negative controls carry named semantics.** `denied` (forbidden-path probes) must return an explicit denial and zero content and mirror the store's path policy exactly — if the policy is reimplemented instead of imported, prove the mirror with a comparison battery; `not_covered` must return zero fabricated results, gated by a coverage threshold that keeps weak junk out — tuned on principle, never per-query special cases.
- **Anti-fabrication invariant.** Every returned snippet must verify as a literal substring of the current source at scoring time, and a content hash's coverage (whole file vs slice) must be pinned on a partial-range record before consumers are built on it — full-range records cannot distinguish the two semantics.
- **Score read-only against live sources.** Record per-query top-k refs, a hit/miss table, and every negative-control outcome. Honest misses stand: a below-threshold score triggers engine fixes and re-runs, never set edits.
- **Degraded-state behavior is part of acceptance.** Missing or corrupt index → rebuild or explicit stale/error marker; a source changed under a built index → explicit stale flag, never a fabricated snippet; fixture decoys (fake secrets/backups outside the whitelist) stay unindexed and byte-unchanged.
- **CJK storage-engine trap.** Do not assume SQLite FTS5/trigram availability, or that the default tokenizer splits CJK runs — probe the runtime and fall back to a custom n-gram/substring index if needed; the SQLite index stays disposable and rebuildable, never the authority.
- **Keep the instrument.** Record the frozen set's path, the scorer's location and its re-run command (plus the lock sha256) in the applied record / consumer note, so a later A/B round reuses the identical instrument and re-verifies the same lock instead of minting a new set.
- **Test the hash guard at the point it actually reads.** An input-override flag (`--query-set <copy>`) may select a structure-only validation path, where a tampered copy exits clean and proves nothing; plant the tampered file at the guard's DEFAULT resolution path inside a fake layout root, invoke WITHOUT the override, and require the refusal exit and error JSON — then re-verify the real frozen file's hash so the probe itself is shown to have written nothing.

### Isolated candidate-tool pilot (A/B before any adoption decision)

The pilot installs and measures WITHOUT touching the incumbent or the global environment; adoption stays a separately authorized round. The pilot's result record is byte-frozen; the keep/trim/delete disposition is a separate note (sidecar rule).

- **Install under a throwaway prefix with every state path redirected** — package-manager isolation first (`npm install --prefix <pilot>/ --cache <pilot>/npm-cache --no-save --no-package-lock --no-audit --no-fund`), then the tool's own env vars (`XDG_CACHE_HOME`/`XDG_CONFIG_HOME`/`<TOOL>_CONFIG_DIR`-style) plus any vendor-documented flag for unstable platform paths. After first use verify config/index landed INSIDE the pilot and the tool's documented default locations were NOT created; rollback = delete the prefix dir. Record actual footprint against the authorization estimate, disclose an overshoot with its composition, and state which boundary actually held (e.g. no model downloads, no model-backend loads).
- **Install scripts may be policy-skipped** (npm `allowScripts`): the install log then proves nothing about native bindings — exercise the tool's smoke path (or a `require()` probe) and list any unbuilt optional components with whether the stage needs them.
- **Restrict the candidate's own benchmark harness to the model-free backend** by importing its harness module directly with an explicit backend list — a keyword-stage trial must never reach vector/rerank paths that trigger model work; if it cannot be filtered, score the raw CLI with your own scorer instead.
- **Corpus view = registered slices mirrored around tool quirks.** If the tool's globbing cannot enter dot-prefixed trees, mirror to dotless paths (`<dot>dir/ → dir/`) with a recorded 1:1 mapping and byte-identical content; confirm the index holds 100% of the view before benchmarking (a wrong mask hiding a silent 3/16 index is the classic trip).
- **Apples-to-apples protocol:** same invocation mode for both arms for the headline latency/context-bytes (CLI-to-CLI; in-process latency is a separate labeled metric), same top-k, frozen set with re-verified lock; one documented scorer produces the acceptance numbers even when the candidate's harness produced the raw run.
- **Threshold arithmetic before the run:** if the incumbent already passes the absolute gate on the frozen set, a "net-new hits ≥ N" criterion is unsatisfiable by construction — pre-register the fallback branch (quality not lower AND ≥20% better warm P95 or context bytes) and treat "keep the incumbent / no adoption" as an expected legitimate verdict; decompose misses by cause group (path-shaped queries vs content-only matching; metadata-only aliases the tool cannot see; tokenizer/AND semantics) so the verdict names structural gaps, not just a score.
- **Security probe battery** (record every raw outcome): fetch by traversal, absolute path, decoy name, and glob-escape must refuse with explicit not-found and a nonzero rc captured from the direct invocation (never through a pipe); junction escape — create with PowerShell (`New-Item -ItemType Junction`; `cmd //c mklink` from git-bash can drop into an interactive cmd and create nothing while appearing to succeed), delete with `[System.IO.Directory]::Delete(path, $false)` (a recursive delete can follow into the target); file symlinks may be elevation-blocked — record as environment-limited, never as passed; a junction planted inside the scan root: prove NON-following by re-scanning and comparing indexed file counts, then remove it and confirm the count returns.
- **Source-change semantics on the view copy:** edit a view file → the tool must not reflect it before an explicit re-index; re-index → incremental pickup; restore → byte-verify file and search. Never experiment on live sources.
- **Zero-write audit:** `find <domain> -type f -newermt '<pilot start>'` excluding the pilot and the round's work dirs; attribute any surfaced file by mtime against previous rounds' records before calling drift (a previous suite's disposable `tests/**/.tmp` index is the usual false alarm).

## 10. Dual-role pre-apply review (staged-batch installs)

Before the §8 gate, dispatch TWO fresh isolated reviewers with non-overlapping mandates. Neither reads the other's report, neither treats the implementer's summary as fact (rule 6), and both are read-only outside their own report path and scratch dir. A retry after a mid-run batch death may reuse the dead attempt's scratch scripts but must re-run and re-derive every number — state that in the retry contract and re-hash the protected surfaces (frozen inputs, live targets) before re-dispatch to confirm the dead attempt left no side effects.

- **Spec reviewer** — requirement-to-evidence mapping (each plan requirement → test names → RED/GREEN artifacts), evidence-chain integrity (re-hash every artifact against the implementation record; mirrors byte-identical to live), disclosure adequacy (deviations, first-failure archiving, declared limits), frozen-input lock re-checks, and publish-set reconciliation: enumerate the new-to-copy files exactly — pre-existing frozen inputs, stage-only tooling, mirrors, snapshots and disposable indexes are excluded by name; a narrative count that disagrees with the actual copy set is a finding, not cosmetics.
- **Quality reviewer** — its own end-to-end re-runs: the full suite at the stage root, the acceptance battery through its own harness (never the implementer's scorer), adversarial probes (path-denial battery vs the mirrored policy, index corruption/deletion self-healing, source-change stale behavior, decoy files byte-unchanged, junction/symlink non-following proven by re-scan count, encoding and determinism), and static scans (execution primitives, hardcoded query/answer literals).
- **Fixed verdict vocabulary**: `approve` / `approve_with_declared_limits` / `approve_with_caveats` / `block`, plus numbered publication conditions (K1…Kn) the applier satisfies one by one and cites in the applied record; a condition that demands clarifying stale wording is discharged in the applied record itself, never by editing already-reviewed bytes; a condition demanding explicit publication approval is discharged by the §8 gate decision itself — its record quotes the authorization basis literally (the owner's continuation instruction plus the scope-doc clause defining the promotion path) and adds an audit note and an immediate-rollback clause so the owner can override after the fact. A scope doc that already defines the gate path is the standing mandate to run it to completion, not a reason to re-confirm each gate. Each report carries an explicit `unverifiable` list and classifies findings blocking / non-blocking with a minimal reproduction. Only approving verdicts on both sides move the batch to the §8 gate.

## 11. Remediation round after a blocked review (v1→v2 re-freeze)

When a reviewer blocks a staged revision, the fix stays in staging and the round becomes a re-freeze, not a fresh round.

- **Pin the fix scope to the blocking conditions and preserve the prior revision as history.** The old implementation record and both reviewer reports stay byte-unchanged; archive the old candidate bytes under a `history/<revision>-final/`-style snapshot and hash that snapshot into the new revision's record.
- **TDD the counterexamples.** RED runs execute the new tests against the OLD bytes (record exit code and failing counts); a minimal fix flips exactly those tests GREEN; then the legacy suite in the same isolated layout, then the combined suite. If a first green run overshoots the fix scope, revert to the minimal fix, re-run canonically, and archive the overshoot under a rename note with its bytes — never delete it. A renamed/archived snapshot directory is disclosed and bound through the note's declared directory; a stale internal path label is not a byte mismatch.
- **Parent verification adds two whole-set checks.** (a) The OLD artifact manifest against disk shows exactly the expected changed set (the re-mediated files, with their new hashes) and `missing == []` — everything else byte-stable. (b) The new manifest recomputes in full, with its self-reference exclusion stated.
- **Re-dispatch BOTH reviewer roles against the new bytes.** A previous approval does not carry to changed bytes; its numbered conditions (and the blocked round's) carry as closure criteria for the new quality review, and the new spec review re-derives its mapping from the exact frozen hashes supplied in the dispatch. Include expected counts for the revision (suite counts, entrypoint matrix size, diff segments) so any mismatch surfaces as a finding.
- **Deviations are evidence.** Overshoot runs, deleted stray artifacts (run audited Python with `PYTHONDONTWRITEBYTECODE=1` or one stray `.pyc` becomes an incident), and harness aborts before persistence each get a note artifact; check the note against disk and carry it into the applied record's limits.

## 12. Byte-level diff replay + freshness for a staged candidate

When the round's review artifact is a diff claiming to transform each live file into its staged revision (sectioned format: `===== <path>` headers, `--- live/<p>` / `+++ staged/<p>` refs, unified hunks; new files as `--- /dev/null`), the parent check is a replay: apply the parsed diff to the CURRENT live bytes and require byte-equality with the staged file per section — that proves the diff describes exactly the intended change and nothing else.

Recipe: read the diff as BYTES (text mode silently eats `\r`); split sections on `(?m)^===== `; per section take the first `--- ` and `+++ ` lines for base/target refs; split hunks on `(?m)^@@ `; parse each header with `-(\d+)(?:,\d+)? \+\d+(?:,\d+)? @@`; apply by walking hunk lines on the first byte — ` ` context (copy+consume), `-` consume, `+` emit — after copying base lines up to the hunk's 1-based start; tail-copy the remainder; join with `\n`.

- **Slice refs by the literal prefix you matched: `--- ` and `+++ ` are 4 bytes each in this format.** An offset copied from a `diff --git` dialect (`+++ b/` = 6) misparses the ref and the follow-up regex dies as `NoneType.group` — derive every slice from the matched prefix, never from another dialect's convention.
- Tagless lines (the `b''` that `split(b'\n')` leaves at EOF) drop naturally, and that same machinery reproduces the trailing newline for `/dev/null` sections (an empty base's tail-copy appends one `b''`), so new-file builds need no special case.
- Assert the replayed set equals the diff-section set AND the implementation record's set (set equality, not a guessed partition — a record that also tracks auxiliary files defeats "aux files will be unrecorded" expectations; a first-run FAIL on expectations is the checker's bug: fix, re-run, attribute both runs).
- **Stale staged set (live moved since staging): the freshness trio runs before replaying.** (a) every replaced target's current hash == the recorded `original_sha256`; (b) every to-be-created path AND its parent dir still absent; (c) reconciliation against the round's earlier live snapshot — recompute every recorded hash now and require the current delta to equal EXACTLY the known intervening merges' additions (any other missing/changed entry is drift ⇒ stop, zero writes). Build the rehearsal copy from the CURRENT live set (latest known layout list ∪ those additions), then overlay the candidate batch.
