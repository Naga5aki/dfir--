# CTF Misc / File-Format Analysis

Analyzing unfamiliar files for hidden data (CTF Misc category, digital forensics, malware triage). The file may be a different type than its extension, embed a second container after a real end boundary, carry steganographic payloads, or be split into shards. Rule of the class: **structure first, decode second — never regex-search the whole disk for a flag before locating the carrier.**

**Output language (this training environment):** trainer-facing replies, phase notes, summaries and Markdown reports go in Simplified Chinese; code, commands, paths, algorithm names and raw tool output may remain English with a Chinese gloss. English compaction notes or material quoted from references never switch the output language.

## Core workflow (per artifact)

1. **Evidence isolation & hashing** — copy the original into an evidence dir (read-only); SHA-256 before AND after analysis; work only on copies in a separate work dir. Never modify/rename/overwrite evidence.
2. **Type verification** — `file` + magic bytes + independent parsers. Extension is a label, not proof.
3. **Structure walk** — write or reuse a marker/chunk walker (JPEG markers, PNG chunks, GIF blocks, segment tables); record every offset/length/CRC. Verify CRCs where present.
4. **Auto-scan, then manual verify** — a bounded signature scanner (PNG/JPEG/ZIP/GZIP only) may propose candidates, but EVERY accepted hit must be re-verified at the byte level (header, trailer/directory, length, container end boundary, extracted hash). Record false positives; automated hits are leads, not proof.
5. **Extract to work** — cut at verified boundaries only.
6. **Format-integrity check of every derivative** — `file`, parser open, chunk/marker walk, SHA-256.
7. **Two independent verifications** — second implementation or independent tool; the two must not share the extraction function (an off-by-one in one implementation gets caught by the other). When the task provides an independent anchor — a known-good hash of the expected decode output, or a structural invariant (total samples ÷ line count = 0, matrix size, fixed protocol field values) — **each implementation must be checked against the anchor separately**. Two implementations that only agree with each other are not validated: a shared wrong structural assumption (bad column width, inverted frequency mapping, wrong channel order) makes both agree while both are wrong.
8. **Bounded execution** — for interpreters (Piet npiet, etc.): verify tool hash against the expected value, run help + a benign minimal test first, ALWAYS use a step limit (`-e`), separate stdout from exit/error messages, and treat repeated loop output as one answer, not many. Apply the same bound to hypothesis ROUTES, not just interpreters: three consecutive attempts on one hypothesis with no new evidence ⇒ stop that route and change the structural hypothesis — micro-tuning forms/directions of a failed route is the classic time sink.

## Technique patterns

### Trailing containers after JPEG
JPEG real end = EOI marker (`FF D9`) found by a marker walk; everything after EOI+2 is trailing data. Cut at that boundary and verify the ZIP triple: Local Header / Central Directory / EOCD — EOCD end offset must equal the file end.
**Pitfall: the ZIP header CRC is the CRC32 of the UNCOMPRESSED data.** Comparing against the compressed stream yields a false MISMATCH. Recompute on the inflated bytes (or let `zipfile` validate).

### Firmware-style self-describing containers
Header: magic + version + segment count; descriptor table: tag(4)+offset(4)+length(4)+crc(4) per entry — check endianness (usually LE). Parse ALL descriptors, recompute CRC per segment vs stored, check pairwise overlaps and off+len out-of-bounds, inspect gaps (table→first segment, file tail) for padding or hidden data. Cut by table offsets, not signature scan.

### Dual-image differencing
Confirm size/mode identity; per-channel diff counts and value sets. Real overlays typically move ONE channel with a constant delta; compression noise touches all channels with scattered values. Outside the diff mask the two images must be pixel-identical. Enhance: |D|×K saturation or mask binarization (white-on-black) for OCR.

### Piet color programs
Strip programs: 2 identical rows ⇒ codel size = 2; each color block's width / codel size = block codel count. Same-hue light→normal transition = push (value = block size); consecutive-block hue/lightness deltas map via the Piet op table (e.g. (5,−1) = out(char)). Block width / codel size frequently decodes straight to ASCII. Run npiet with `-cs <size>` and `-e <step limit>`; keep stdout and exit info in separate files.

### Multi-shard reassembly
Per piece: magic + embedded index + total + payload_len + payload CRC32. Order by EMBEDDED index, never by filename. Verify each piece CRC, index-set completeness, then validate the reassembled file's full structure (signature, chunk walk, zero trailing). **Index-less byte-interleaved shards (RAID0-style striping)**: when pieces carry no index and no declared volume order, decide strip width and part order by STRUCTURE SELF-CHECK — re-mix candidate orderings until the product parses as the target container (ZIP EOCD at end + CRCs pass); never trust filenames or intuition; a wrong strip must corrupt the parse (negative control).

### Palette/GCT LSB extraction
Read the carrier's raw bytes in file order and take `byte & 1` directly. Do NOT XOR against any theoretical palette formula — the delta mask is message⊕formula noise, not the message. Pack MSB-first (first bit = MSB); first 16 bits = big-endian payload length; read that many bytes. Prove only the message region was modified by matching the untouched-region LSB stream against the formula.

### Low-contrast / anti-aliased text and OCR limits
- Low-contrast text spreads across neighboring palette indices: exact-index extraction yields only stray pixels — rebuild glyphs with a luminance threshold (R+G+B).
- OCR is unreliable for isolated punctuation (a lone `}` can be classified as S/s), drops trailing underscores, and merges `s_` into `S`.
- Pixel height distinguishes lowercase vs full-height only — punctuation braces occupy full cap height too, so height cannot separate a letter from a brace. Judge glyphs by skeleton (spine position, hooks, bars), and quantify with template matching (render reference glyphs, Dice coefficient).

### Duplicated pixel-column layout
Multiple copies of the same text: locate each copy's column range and gaps; verify gaps are pure background; compare copies column-wise (diff pixel distribution, per-column shift histogram — a near-zero dy histogram with edge-scattered diffs means rendering variation, not a column permutation). Deduplicate to a single copy as the repaired image and hash it.

### Windows credential-attack traffic (SMB spray / WinRM / RDP / PTH)
Reading a Pass-the-Hash-style capture: the wire never shows whether a password or a hash was replayed — report the structural chain, keep the credential FORM as inference, and record NTLMv2 material verbatim.
- **NTLM workstation fingerprint:** `JCIFS_127_0_0_1` = Java jcifs default hostname — a tooling client, not a host. An auth domain field carrying the target's IP is tool behavior; recover the real NetBIOS/DNS domain and host from the NTResponse TargetInfo blob (UTF-16LE runs after `01 01 00 00`).
- **Spray reading:** each attempt = type1→type2→type3 (`ntlmssp.messagetype` 0x1/0x2/0x3); the per-attempt verdict is the SERVER-side response after type3 — client requests also carry `smb.nt_status 0x0`, so count/filter from the server direction. A hit that immediately TreeConnects IPC$ then disconnects and logs off within milliseconds is credential VALIDATION (that is the success frame); capture `ntlmssp.ntlmserverchallenge` + `ntlmssp.auth.ntresponse` verbatim.
- **WinRM channel:** `/wsman` POSTs on 5985, 401→type1/2/3→200 per session; after auth the bodies become `multipart/encrypted` (HTTP-SPNEGO-session-encrypted). With NO credential material this is a hard boundary — read what stays visible (`OriginalContent: …;Length=N` sizes, session timing) and correlate victim-side side effects. **But once the credential material is recovered (cracked NTLMv2 / PTH), the session keys ARE derivable — do not stop at "encrypted":** derive sign/seal keys per the NTLM/SPNEGO spec against an authoritative implementation, verify every message by its checksum, merge messages split across TCP segments; commands and output become fully recoverable (recipes in `references/day7-network-techniques.md`).
- **Attacker delivery fingerprints:** `Server: SimpleHTTP/0.6 Python/x.y` = `python -m http.server`; a victim GET with UA `CertUtil URL Agent` / `Microsoft-CryptoAPI/…` = certutil staging. Identify payloads structurally (PE machine/sections/TimeDateStamp + string clusters), never by filename.
- **RDP:** the intended username leaks pre-TLS in the X.224 `mstshash=` cookie (read via `-V`; there is no `rdp.cookie` field); `requestedProtocols`/`selectedProtocol` (0x0b CredSSP+NLA vs 0x01 TLS-only) exposes deliberate NLA-downgrade retries; server host identity from the TLS cert CN; a long established session with two-way app data ≠ the RST-failed retries before it.
- **RDP decrypt chain (when the server cert/key is recovered, e.g. a pfx pulled from a decrypted SMB3 session):** TLS 1.0 RSA sessions (cipher 0x002f) are decryptable with a self-written decryptor — pitfalls: the RSA-decrypted premaster carries a version prefix (`03 03`); the TLS 1.0 PRF splits the 48-byte secret into S1 (MD5) + S2 (SHA1), NOT the TLS 1.2 PRF; the padding field value = padding bytes − 1 (RFC 2246). Establish a reference (a tool's own TLS debug output) before debugging your keyring. To parse the decrypted fastpath input set the `tls.keys_list` protocol value to `tpkt` (port 3389 decodes to TPKT; the RDP dissector is a heuristic on the TPKT table, not a tcp.port registration) — `rdp.fastpath.*` fields then appear and the keystroke stream is readable.
- **A byte-pattern hit is not protocol traffic:** map the raw file offset to its frame (pcapng EPB walk) before interpreting; transferred binaries legitimately contain attack-looking strings (mimikatz carries `ldap_connect`/AD-schema templates). Grep the payload file separately from the capture.

### USB HID captures (USBPcap / pcapng)
USB captures arrive as pcapng with a USB link type: split frames by DEVICE and ENDPOINT first — mixing devices is the first failure mode. A HID keyboard interrupt-IN report is a PRESSED-SET SNAPSHOT, not a key event: diff consecutive reports to derive press/release (an identical repeat = key held / auto-repeat, not a new press); fold BACKSPACE into the text (delete the last character) and keep the correction trail — the candidate worth testing is the text AFTER corrections; map modifiers (Shift et al.) explicitly since they change the character set. Mouse deltas: integrate only as a bounded overview — if no text/structural signal emerges within a few attempts, stop the branch (visualization tweaks are a time sink). Always hand a recovered candidate to a downstream check (container header/CRC, filesystem) before trusting it — an unvalidated keyboard trajectory is a lead, not a password. (From a live USBPcap reproduction; no independent variants yet.)

### Encrypted per-session payloads & field-derived keys
Uniform-length payloads across many short sessions often mean EACH session carries its own independent object (own key, own container) — not one fragmented stream. Decrypt and validate ONE session end-to-end (decrypt → identify structure → close the loop) before touching the others; cross-session assembly order and port side must come from structural evidence, never assumption — a wrong session model invalidates every downstream test. When the rule hints a derived key ("calc the md5 of the port"), sweep the whole form matrix IN ONE PASS: both field directions × {raw digest bytes, lowercase hex TEXT, uppercase hex TEXT} × {AES-ECB first (independent short blocks), CBC/CTR, RC4, XOR}, and judge every candidate by STRUCTURE (valid container? parses? CRC?) — never by "it ran". When the full matrix misses, switch the STRUCTURAL hypothesis (independent objects vs one stream, wrong layer) instead of micro-tuning forms; three consecutive attempts with no new evidence = abandon the route (Bounded execution discipline).

### Document & text steganography (PDF / OOXML / SNOW / zero-width / NTFS ADS)
PDF: `qpdf --show-xref`/`--show-pages` first — **`/ObjStm` members (compressed) vs the page content stream (often an uncompressed standalone object) are separate facts; a stream object can't be an ObjStm member, so verify per object before claiming the content stream came from an object stream**; then `--qdf --object-streams=disable --decode-level=all` expands; invisible text via fill-color operator (`1 1 1 rg` white-on-white vs `0 0 0 rg`); attachment chain Names/EmbeddedFiles → Filespec → EF/F → EmbeddedFile; `--show-attachment=key` (no --save-attachment in 12.x). OOXML: ZIP-part enumeration, relationship Target normalized relative to the source part, comments.xml + media metadata (PNG tEXt) combined by explicit part labels. Macro-enabled OOXML: macroEnabled ContentType + vbaProject.bin CFB magic + CFB directory walk (n_FAT@44, NOT @56); **real VBA modules parse dir-stream MODULE records → MODULEOFFSET/TextOffset → MS-OVBA container from TextOffset (never judge compression by first byte 0x01); a minimal training CFB with VBA-shaped plaintext is a sample-specific label, not a standard VBA project**. SNOW: trailing whitespace has FOUR statistics (full trailing / spaces / tabs / spaces-after-last-tab) — the last group is not the whole line; `-C` compressed extract — mode must match the payload (wrong mode fails silently); decode "success" ≠ correct message (single-char tamper is silent) — validate the extracted message shape (prefix/printability) before use; **tool first — both modes within the first minute; hand-reading capped at 1 profiling round (2 no-hit rounds ⇒ switch)**; CR/LF stats as independent check. Zero-width: code-point bit stream (ZWSP/ZWNJ mapping, MSB-first, inverted-mapping control) often yields a "stream=...;encoding=..." instruction. NTFS ADS: `7z l -slt -sns` audit → extract to NTFS → `Get-Item -Stream *` confirms real stream. **Static presence ≠ execution** for PDF JS / macros. Full recipes: `references/day8-doc-text-techniques.md`.

### Lightweight forensics (SQLite WAL / Git bundle / registry hive / Chromium History)
**Current state ≠ historical state**: SQLite WAL frames carry older page versions (parse the b-tree leaf record via varint/serial types and prove the row is absent from the current read-only SELECT; **page versions only prove content differed — they cannot determine UPDATE vs DELETE+INSERT, because without AUTOINCREMENT a deleted max ROWID is reusable by a later INSERT**); Git deleted commits still reference the blob (`git show <commit>:<path>`); registry MRUList ordering (not alphabetical) assembles values. **Timestamps: confirm epoch/unit first** — Unix µs vs FILETIME (100 ns since 1601) vs WebKit (µs since 1601); report raw integer + interpretation + ISO 8601 UTC; identical FILETIMEs only prove stored values are equal, not write count. **regf header checksum = XOR of the 127 LE DWORDs over 0x000–0x1FB vs stored @0x1FC — a mismatch means debug offset/endianness/loop/truncation first, never blame a "generator variant"** (that false conclusion came from summing instead of XORing). Registry hive binary layouts (NK name_len@0x48/name@0x4C single-byte names; VK sig/name_len@2/len@4 with `0x80000000`=inline/data_off@8/type@0xC/name@0x14; cell = 4-B signed size; offsets relative to first HBIN data area +0x1000) are unforgiving — see `references/day9-forensics-techniques.md`.

### Quoted-Printable (ASCII-armored) ZIP hidden in EXIF
`strings` shows the carrier as literal `PK=03=04=14=00...` with entry names readable inline — a ZIP encoded as ASCII: non-printable bytes become `=XX` hex, and **line-wrapped with `=`+LF soft line breaks** (≈76 chars/line). A naive `=XX`-only decode mis-decodes names split at a wrap (e.g. `h=\nint.txt` is "hint.txt" — the `=\n` is a continuation, not data). Decode with `quopri.decodestring` (stdlib) which handles soft breaks; then parse local headers/Central Dir/EOCD and verify every CRC. **Do not assume the decoded stream is one ZIP: decode the WHOLE segment tail, then account for every byte — the outer zip's EOCD end offset may leave trailing bytes that are padding + a secondary hint (e.g. zero padding followed by UTF-16LE text like `w\x00h\x00e\x00...`).** Where it hides: a large `0xEA1C` UNDEFINED entry in the EXIF IFD/ExifIFD; also check a second 0xEA1C blob for payloads (it may be pure zero padding). Cover-check the whole JPEG: segment walk must end exactly at EOI with zero trailing bytes. **Decode with QP -> then immediately diff LH vs CD flags: the outer container may be FAKE-ENCRYPTED (CD GP-flag bit0=1 while LH bit0=0, and/or unzip says "unable to get password" though data is stored deflated normally) — fix by clearing bit0 ONLY in the outer's own CD entries (delimited by its EOCD cdoff..cdoff+cdsize), never signature-scan the whole stream: a nested stored zip inside the stream contains the same `PK\x01\x02` signatures and a blind scan corrupts it (observed: byte 141 of the nested zip patched → bad CRC).**

### WinZip AES-encrypted ZIP entry (method 99) — manual AE-2 decrypt
Entry signature: method=99 (0x63) + GP flag bit 0; extra field `0x9901` = id 0x9901, size 7, version(2), vendor "AE"(2), strength(1: 1/2/3 = AES-128/192/256), inner method(2). Layout: **salt = 16 bytes for AES-256 (8/12 for 128/192)** + 2-byte password verifier + ciphertext + trailing **10-byte HMAC-SHA1**; csize covers all four. AE-2: keymaterial = PBKDF2-HMAC-SHA1(pw, salt, 1000, 66) → enckey=km[0:32], HMAC key=km[32:64], **verifier check = km[64:66] == stored 2 bytes** (not a CRC); AES-256-**CTR with 128-bit counter, little-endian increment, initial value 1** (pycryptodome `Counter.new(128, initial_value=1, little_endian=True)`); HMAC = SHA1(km[32:64], ciphertext)[:10]. Then inflate (inner method 8) and verify ZIP CRC. **AE-1 vs AE-2 differ ONLY in CRC handling — BOTH are CTR+HMAC, never CBC.** AE-1 stores the real CRC32 of the plaintext (verify after inflate); AE-2 stores CRC=0. The 2-byte password verifier is keymaterial[64:66] (NOT crc32(pw)&0xFFFF — that formula is the ZipCrypto check byte). Note: the very first manual decrypt attempt can fail on salt length — AES-256 salt is 16 bytes (128→8, 192→12); a failed verifier check with 8-byte salt on a strength=3 entry means wrong salt size, not wrong mode. Verification of this challenge's entry: extra version=1 (AE-1), stored CRC matched the computed CRC of the inflated plaintext. pyzipper (pip, python3) handles all this for candidate testing/bruteforce (verifier check = fast rejection). For structured hints (e.g. `hint:do_u_like_xxx` where xxx is unknown), prefer john's mask attack over python bruteforce: `zip2john flag.zip` → `john --mask='do_u_like_?l?l?l' hash` (cracks 36³ in <1s; ?l lowercase, ?d digits, ?a all).

### ZipCrypto + Store known-plaintext (bkcrack) — attack economics
Store (method 0) + ZipCrypto entries ⇒ sparse known-plaintext attack. Verified in live solve (2026-10, secret.zip "Zip doctor", solved in ~12 min):
- The candidate space is governed ONLY by known bytes at positions <= attack index; appending constants DEEPER in the sequence (e.g. pyc [30:46)) does NOT shrink it (measured: identical space count) — speed comes from closing gaps in the EARLY prefix, never from tail bytes.
- Run 2-4 variants in parallel (-j6 each); prioritize the MINIMAL-assumption variant (near-certain constants only). Measured: the 849k-space minimal variant hit at ~20% while smaller-space variants with extra guesses (mtime/size) lagged — candidate enumeration order differs per variant. Kill losers the moment one hits (verify the other is truly redundant, not a different hypothesis).
- Python 3.13 .pyc known-plaintext map (10-sample verified): [0:8) magic+flags; [8:12) mtime = int(source fs mtime) — recoverable from the zip's NTFS-extra FILETIME of the .py entry; [12:16) source size; [14:16) ==0000 while size<64KB; [16:29) == e3 + 12x00. [30:38)/[39:44)/[45] hold across samples but do not accelerate.
- Verify decryption twice: `-D` whole-archive + per-entry `-d`; cmp the two outputs and CRC32-reconcile EVERY entry against the central directory. Challenge-generated zips may share one equivalent key state across entries (one key set decrypted every entry, CRC-verified) — still CRC-check each entry.

### Multi-source correlation / comprehensive event investigation (main + decoy cases)
One main `case_id` spread across access log / PCAP / browser history / registry hive / a disguised file, with a decoy case to exclude. **`sequence` orders fragments for assembly (1..N continuous, no dupes) and NEVER orders the timeline — build time exclusively from each source's own timestamp fields (log UTC seconds / WebKit µs-1601 / FILETIME 100ns-1601 / HTTP header ISO).** **Object hash must verify across three sources byte-for-byte: protocol header declared value (e.g. X-Artifact-SHA256) ⇄ app record (Chromium `downloads.hash` BLOB = raw 32-byte SHA-256) ⇄ file on disk + reassembled response body.** Content-Type/extension are claims (a `image/jpeg` response whose body is `50 4B 03 04` is a ZIP — verify magic + `testzip()`); manifest `created_at` ≠ download time ≠ Registry LastWrite. Exclude a decoy on ≥2 independent reasons (case_id differs, sequences discontinuous, object 404/never downloaded, fragments meaningless). Cleanest PCAP body export: `tshark -Y "http.response" -T fields -e http.file_data` (hex); `-z follow,tcp,raw` hex sits AFTER the `Node 0/1:` lines. **Capture every structured field twice from independent implementations (TShark `-e http.response.line` AND raw TCP-seq reassembly + CRLF split — `http.header` is not a valid TShark 4.2.0 field) and require byte-identical results; keep raw hex+ASCII of each field; dual-decode Base64 + re-encode check; assert same case_id + sequence 1..N continuous before assembling; a semantically odd decoded fragment is a transcription red flag, not evidence (Day 10: Base64 field mis-transcribed between tool output and report → 90/100).** Full recipe: `references/day10-correlation-techniques.md`.

## Verification & honesty rules
- Keep Observation / Inference / Alternatives / Conclusion distinct; a single parser's output never proves behavior.
- Re-check your own scripts too (e.g., wrong CRC basis) and report the correction — do not hide it as if first-try correct.
- **Reference solutions (writeups) are claims, not ground truth**: reproduce their chain from the raw artifacts; the recurring defects are implicit values the code never states (chunk/entry lengths it relies on) and nonstandard variants of standard formulas — implement the standard form, compare, and record each deviation.
- **Writeup reconciliation (post-solve review) separates knowable-then from hindsight**: detours go in the six-field format (错误判断 / 被忽略的信号 / 形成原因 / 时间损失 / 更快的判断方式 / 下次停止条件) built ONLY from information available at the time; reproduction recomputes the WP's key conclusions from the original artifacts (never copy WP intermediates); a method earns `Transfer-Validated` only when the original reproduction AND all condition-changing variants pass with negative controls rejecting as designed. Procedure + variant/negative-control designs: `references/writeup-reconciliation-and-transfer-verification.md`.
- **Recorded values (hashes, sizes, counts) must be copied VERBATIM from live command output — never padded, recalled, or "completed" from a prefix. A 64-char SHA-256 whose tail wasn't observed is fabricated evidence (teacher-corrected on Day 9); verify sample hashes from three independent sources (Get-FileHash ⇄ SHA256SUMS ⇄ per-member recompute from the outer archive).**
- Long-term memory keeps only generic reusable methods; reports keep the specifics (flags, hashes, one-time offsets).
