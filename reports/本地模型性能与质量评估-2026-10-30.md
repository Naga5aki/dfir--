## 0. 结论摘要

1. **当前配置没有达到 30 token/s，更没有达到 40。** 受控三重复的 decode 均值为：短输入 27.65、约 12K 26.00、约 32K 25.13、约 56K 22.57 token/s。全部 `cache_n=0`、生成 512 token、无截断。【本机实测】
2. **当前真正的瓶颈不是“GPU 算力没跑满”这么简单。** 短输入 GPU 利用率中位 68%、功耗中位 131W；56K 时长文把利用率推到 85%、功耗中位 161W、温度中位 75°C。瓶颈是：2 个主干块仍在 CPU 造成的每 token 串行等待、稠密权重读取的带宽效率、长上下文注意力成本，以及仅约 386MiB 的空闲显存。【本机实测】
3. **功耗结论要纠正：当前 `Current Power Limit` 是 175W，不是 65W。** 旧分析里的 65W/SW Power Cap 是野兽模式生效前的状态；现在 175W 限制生效，长文负载中位 161W、峰值采样 171.6W（另有 12K 阶段瞬时 209W 的异常尖峰），温度未触发降频。不要再按“65W 被锁死”排查。【本机实测】
4. **`-ngl 64` 的确把 blk.0 / blk.1 留在 CPU，输出层已在 GPU。** 源码 `i_gpu_start = max(65 + 1 − 64, 0) = 2`；但“64/66 层”里的 blk.64 是未加载的 MTP 占位块，真实主干是 64 层，当前实际是 62 个主干块在 GPU、2 个在 CPU。`-ngl all` 的真实增量只有 324.9MiB，不是把整个模型再搬一遍。【配置/源码确认】
5. **原生 MTP 是唯一有机会把 12K/短输入推到 40 的模型内手段，但它没有被本机验证过，而且 64K 下显存很紧。** MTP 权重 227.9MiB + 单层 MTP KV 136.0MiB（**需显式把草稿 KV 也设为 q8_0；该版本草稿 KV 默认 F16，64K 下是 256MiB**）+ 目标 `embd_nextn` 缓冲约 10MiB + 未实测图/工作区 100–250MiB；与完整卸载叠加约 +0.78–0.95GiB（草稿 q8）或 +0.90–1.07GiB（草稿 F16）。当前空闲 386MiB，必须先释放其他 GPU 应用。MTP 草稿每步还要复用 833.6MiB 的输出头，接受率不够时可能持平甚至更慢。【配置/源码确认】【估算】【待验证假设】
6. **在 64K 下，40 token/s 在 56K 输入上很可能不现实；30 token/s 在短/12K 有希望，56K 需要 MTP 高接受率且显存/功耗都过关。** 当前 56K 22.57 到 30 需要 1.33×，到 40 需要 1.77×；仅靠完整卸载（估算 1.05–1.20×）不够，必须叠加 MTP 或其他草稿机制。【本机实测】【估算】
7. **“得到正确且完整答案的总时间”与 decode token/s 不是一回事。** 56K 下首 token 约 64.8s，512 token 解码约 22.7s；即使解码从 22.57 提到 40，总时间也只从 87.5s 降到 77.6s（约 11%）。长文场景更该优化 prefill、前缀/状态缓存和避免重复 prefill。【本机实测】【估算】
8. **前缀缓存是本机已实测的巨大总时间杠杆。** 同一 11,870-token prompt，冷启动 `prompt_ms=12,187`，第二次 `cache_n=11,866`、`prompt_ms=119.5`；128 token 输出的总墙钟从 16.9s 降到 4.8s，decode 速度不变（27.1 token/s）。【本机实测】
9. **质量不能假定“当前已正确”。** 一道可验证的数论题（正确答案 8120）在 2048 思考预算下正好用满 2048 token，给出错误答案 18250；4096 预算在 4608 输出上限内仍未完成，不能据此判断更大预算有效或无效。55K 长文的唯一字段定位在给足 256 输出 token 后通过（时间和哈希都对），但只是一道简单检索题。【本机实测】
10. **本轮没有实施任何优化，因此不能称“优化成功”。** 下一步应申请维护窗口，按 Stage A → B 的顺序实测；只有速度超过波动、质量未发现明确退化、64K 连续运行稳定，才采纳。

### 1.4 GPU/CPU 放置与显存账目

本机版本源码 `src/llama-model.cpp:1667`：

```cpp
const int i_gpu_start = std::max(n_layer_all + 1 - n_gpu_layers, 0);
```

本模型 `n_layer_all=65`：
- `-ngl 64` → `i_gpu_start=2` → `blk.0`、`blk.1` 在 CPU；`blk.2..blk.63` 与输出层在 GPU；`blk.64` 是 MTP 槽位，未启用时没有加载张量。
- `blk.64` 是 MTP 占位块；未启用 MTP 时它的张量被 `TENSOR_SKIP` 跳过（`src/llama-model.cpp:3898-3900`），启动日志明确出现 `unused tensor blk.64.* -- ignoring`。
- 因此 **`-ngl 64` 实际是 62 个主干块在 GPU、2 个在 CPU、输出在 GPU**；“offloaded 64/66 layers” 里的 64 包含不存在的 MTP 槽位和输出层，不能理解成“64 个主干层全在 GPU”。
- `-ngl all` 解析为 `-2`，`n_gpu_layers()` 对负数返回 `n_layer_all+1=66`，即真正把 64 个主干块 + 输出层全部放 GPU（输入 `token_embd` 始终在 CPU，源码注释明确说 offload 输入层收益很小）。【配置/源码确认】

字节账目（来自 GGUF 完整张量目录）：

| 项目 | 字节 | 大小 |
|---|---:|---:|
| 当前 `-ngl 64` GPU 权重（blk.2–63 + output + output_norm） | 11,449,528,064 | 10.66 GiB |
| 当前 CPU 权重（blk.0/1 + token_embd） | 886,941,952 | 845.9 MiB |
| `-ngl all` 增量（blk.0+blk.1） | 340,637,952 | 324.9 MiB |
| MTP 权重（启用时） | 238,983,168 | 227.9 MiB |
| 主模型 64K KV（16 层 ×4 KV heads×256×65,536×K/V q8_0） | 2,281,701,376 | 2.125 GiB |
| MTP 单层 64K KV（启用时） | 142,606,336 | 136.0 MiB |

### 1.6 瓶颈排序

1. **显存余量是路线选择的第一道闸门。** 当前空闲 386MiB；完整卸载 + MTP 估算需 0.78–0.95GiB 增量（草稿 KV q8；若用默认 F16 草稿 KV，则为 0.90–1.07GiB）。不释放其他应用，Stage B 很容易 OOM 或落进共享显存。
2. **2 个 CPU 主干块的串行等待。** blk.0/1 共 324.9MiB，每 token 要先在 CPU 上算完再进 GPU；短输入 GPU 利用率只有 68%，与这种气泡一致。完整卸载的收益估计 5–20%，但未实测。
3. **稠密模型的权重读取带宽。** 当前 GPU 权重 10.66GiB/token 量级；27.65 token/s 对应约 316GB/s 有效读取（11.45GB×27.65）。按公开的 16GB GDDR7/256-bit/约 896GB/s 上限估算，约 35% 利用率（该 896GB/s 是公开规格，未从 NVIDIA 官方页面逐项核对）；这不是 profiler 计数，且未扣注意力/采样/缓存，但说明“算力已充分利用”不成立。40 token/s 对应约 458GB/s（约 51% 上限），需要更高内核/调度效率。
4. **长上下文注意力成本。** 从短输入 27.65 降到 56K 22.57（−18%）。56K 时 GPU 利用率 85%、功耗 161W，说明不是“GPU 闲着”，而是每 token 多了 16 层 full attention 的 KV 读取/注意力计算。
5. **MTP 的接受率与草稿成本。** 草稿每步复用 833.6MiB 输出头 + 227.9MiB MTP 块；接受率低时净收益可能为负。这是当前最大的未知数。
6. **prefill/TTFT 与重复 prefill。** 56K TTFT 64.8s，占总时间约 74%；decode 提升 30→40 只省约 10s。提高 ubatch、保留长前缀状态、避免重复 prefill 可能比 decode 更值钱。
7. **采样/调度开销。** 248K 词表、backend sampling 关闭；估计占每 token 数毫秒，优先级低于 1–6。
8. **功耗/温度。** 长文已到 161W 中位、79°C 峰值；不是当前第一瓶颈，但会限制叠加优化的上限。

## 3. 本机实测基线

### 3.1 方法

- 单请求、非并发；每次请求前 `/metrics` 的 `requests_processing=0`、`requests_deferred=0`。
- 统一 chat 模板、`reasoning on`、`enable_thinking=true`、`reasoning_budget_tokens=2048`（服务端默认）、采样 temp 1.0、top_k 20、top_p 0.95、min_p 0.05、repeat_penalty 1.0、seed 42。
- 每条固定生成 512 token（`ignore_eos=true`），不用 512 截断冒充完整解题。
- `cache_prompt=false`；每条使用唯一 nonce，`timings.cache_n` 全部为 0。
- 每条重复 3 次；报告原始值、均值、极差、样本标准差，不包装 P95/显著性。
- 输入为本地生成的合成中文取证材料，不包含用户私人对话或日志内容。
- TTFT 为 `prompt_ms + 一个 decode step` 的估算，不是 streaming 首 chunk 直接测量；56K 时误差相对很小，短输入时约一个 token 的误差。
- 服务端 `timings` 直接给出 `prompt_ms`、`predicted_ms`、`predicted_per_second`；完整 JSON 原始记录在 `D:\ForensicsAgent\bench\*_raw.jsonl`。
- GPU 遥测用 `nvidia-smi --query-gpu=... -l 1` 每秒采样；专用/共享显存用 Windows `GPU Process Memory` 计数器。

### 3.4 有前缀复用的对照（重要）

同一 11,870-token prompt，`cache_prompt=true`，生成 128 token：

| 运行 | cache_n | prompt_ms | prompt token/s（服务端口径） | decode token/s | 总墙钟 |
|---|---:|---:|---:|---:|---:|
| 第一次（冷） | 42 | 12,187.1 | 970.5 | 27.11 | 16.91s |
| 第二次（同 prompt） | 11,866 | 119.5 | 33.5（分母含缓存，不能当真实 prefill 速度） | 27.14 | 4.83s |

- 第二次 11,866/11,870 token 命中 LCP 缓存，TTFT 从约 12.2s 降到约 0.12s；总时间 16.9s→4.8s。
- decode 速度完全不变（27.1 token/s），说明缓存改善的是 prefill，不是 decode。
- 这条实验只证明“同一 slot 内连续相同前缀”有效；如果中间插入其他请求把长状态挤出，`--cache-ram 512` 无法保存 56K 状态（日志显示 2,462.75MiB > 512MiB，跳过）。这正是 Stage C1 要测的内容。
- 对于真实 agent，稳定的 system prompt、工具定义、长文档前缀可以显著降低“正确完成任务的耗时”，优先级不应低于 decode 优化。

### 3.5 质量探针（小样本，不是质量回归）

#### 3.5.1 数论题（可验证）

题目：求最小的正整数 n，使 n! 十进制末尾恰好有 2026 个零。正确答案 **8120**（Legendre 公式：`Z(8120)=2026`，`Z(8119)=2025`）。

|---|---:|---:|---:|---|---|---|
| math_budget_2048 | 2048 | 2048（正好用满） | 3,183 | stop | **18250，错误** | 预算被强制结束；模型把“末尾零”错算成 floor(n/10^k)，是模型能力/方法错误，不是速度配置造成的 |
| math_budget_4096 | 4096 | 4096（正好用满） | 4,608（max_tokens 上限） | length | 未完成最终答案 | 输出上限不足，**不能据此判断 4096 预算有效或无效**；质量实验必须给足 `budget + answer + margin` |

- 这条探针说明：当前 2048 预算在硬题上确实会绑定；不能把“保留 2048”理解为“质量不受影响”。也说明单题错误不能归因于提速方案，必须做配对题集。
- 更大预算是否改善正确率，需要独立质量实验（按请求 `reasoning_budget_tokens` 覆盖，不必改生产配置）。

#### 3.5.2 55K 长文精确字段定位

|---|---:|---:|---:|---|---|
| 第一次 | 128 | 55,483 | 98 | length | 只输出时间，哈希被输出上限截断；**测试设计错误，不算检索失败** |

- 也再次说明：质量测试必须给足输出预算；512 token 或 128 token 的截断不能用来判断模型“变笨”。

### 3.6 基线局限

- 合成 prompt，不是用户真实任务；速度主要受长度/注意力影响，但仍可能有内容相关差异。
- 3 次重复只能给出波动范围，不能证明 P95 或统计显著性。
- 没有做 10 分钟单一条件持续测试；32K+56K 矩阵连续约 7.4 分钟，温度峰值 79°C、无错误，但不等于正式 10 分钟验收。
- TTFT 是估算，不是 streaming 首 chunk；排队时间为 0（请求前 `requests_processing=0`）。
- 没有逐层 profiler；放置结论来自源码 + 显存账目，加载日志没有输出 `load_tensors` 逐层行。
- 没有测试接近 64K 的输入（56K 已留 9K 输出余量）；64K 满输入无法同时留出回答空间，不能作为服务配置。
- 没有测试 MTP、完整卸载、backend sampling、ubatch、threads、cache-ram 改动；这些仍是待验证假设。

## 4. 候选优化路线（按证据强度与预期价值排序）

### A. 释放其他 GPU 应用 + 完整 GPU 卸载（第一优先）

**解决哪个瓶颈**：2 个 CPU 主干块的每 token 串行等待；短输入 GPU 利用率 68% 的气泡。

**为什么可能提速**：`-ngl all` 把 blk.0/1 约 324.9MiB 移到 GPU，消除 CPU→GPU 的层间等待；权重精度、KV 类型、上下文、思考预算都不变。按 CPU 读取 325MiB/约 60GB/s 估算约 5.4ms/token，占当前 36ms/token 的约 15%；实际串行开销可能更高或更低，估计 1.05–1.20×。【估算】

**何时无效/更慢**：
- 显存不足导致 OOM、共享显存增长或 WDDM 抖动，速度反而下降。
- CPU 层实际被高效重叠，完整卸载只提升 <5%（在测量波动内）。
- 长文 56K 的注意力/功耗成为主瓶颈，完整卸载只改善很小一部分。

**精度/采样/上下文/思考是否变化**：权重、KV 类型、上下文、思考预算不变；CPU 与 GPU 内核的浮点求和顺序可能略有差异，贪心输出不保证逐字相同；需质量回归。

**额外内存**：权重 +324.9MiB；计算图缓冲可能小幅增加（未实测）；建议至少留 0.5GiB 余量。

**如何证伪**：同输入、同采样、同预算，3 次重复；若 decode 均值提升 < max(5%, 2×基线标准差) 或 56K 出现 OOM/共享显存持续增长，则不采纳。

**回滚**：`-ngl` 改回 `64`，停止/启动计划任务，验证 `/props n_ctx=65536`、`/metrics requests_processing=0`。

### B. 原生 MTP（在 A 通过后；唯一有机会到 40 的模型内路线）

**解决哪个瓶颈**：目标模型每个 token 都要读一遍 10.66GiB 权重；MTP 用一次目标验证批量接受多个草稿 token，把“每 token 一次权重读取”变成“每步一次”。

**为什么可能提速**：qwen35 原生单 MTP 头，GGUF 有 blk.64 张量；该版本 `graph_mtp` 支持 `n_layer_nextn==1`，`common/speculative.cpp` 的 draft-mtp 实现支持单头、n_max 1/2/3。目标模型负责验证，草稿不直接决定输出。【配置/源码确认】

**关键反证/何时无效**：
- 草稿每步要读 MTP 块 227.9MiB + 目标输出头 833.6MiB；不是免费。若每步平均只接受 1 个 token（草稿基本全被拒），可能持平或更慢。
- 64K 下 MTP 额外约 0.46–0.61GiB（不含完整卸载），当前空闲 386MiB；不释放显存就可能 OOM。
- 目标模型被设置为输出 `embd_nextn`，即使不接受草稿也有少量额外开销。
- 启用 MTP 还要在草稿 context 上处理一遍 prompt 来填充单层 KV；56K 的 prefill/TTFT 可能略增（未量化），所以“decode 变快”不等于“总时间同比下降”。
- 长文 56K 已接近 175W 功耗上限；MTP 提高利用率后可能更频繁触顶。
- MTP 在本机该组合上**从未运行过**；“引擎支持 + 张量存在”不等于“已正常跑通”。

**精度/采样/上下文/思考是否变化**：验证路径按目标分布采样；但温度 >0 时 RNG 顺序改变，具体文本不同；贪心可用于确定性配对。上下文仍 64K；思考预算不因 MTP 改变。另需注意：该版本 `common_params_speculative_draft.backend_sampling` 默认 true（`common/common.h:335`），MTP 草稿的 top-k 可能在 backend 上执行；这与全局 `--backend-sampling` 不是同一个开关，`/props` 的 `backend_sampling=false` 只代表主采样。它只影响草稿候选/接受率，不应改变目标验证分布，但实验时必须记录。

**额外内存**：权重 +227.9MiB；MTP KV +136.0MiB（64K，**显式草稿 q8_0**；默认 F16 为 256.0MiB）；目标 `embd_nextn` +10MiB；图/工作区 100–250MiB（估）；与 A 合计 +0.78–0.95GiB（草稿 q8）或 +0.90–1.07GiB（草稿 F16）。

**如何证伪**：记录 draft/accepted/drafts、实际输出 token 数；若接受率低、decode 无提升或质量回归，淘汰。不要用 synthetic acceptance。

**回滚**：删除 `--spec-type` 与 `--spec-draft-n-max`，恢复 `-ngl`（如需），重启验证；保留 MTP 失败日志。

### C. 独立测试项（不要与 A/B 混在一起）

#### C1. 前缀/状态缓存（已实测有效，优先级高）

- 12K 同 prompt：冷 12.2s prefill → 热 0.12s，总时间 16.9s→4.8s（128 输出）；decode 不变。
- 56K prompt state 约 2.46GiB，超过 `--cache-ram 512`，被跳过；把 `--cache-ram` 提高到 3072/4096 可让长状态在 slot 被挤出后恢复。
- 这不改变 token/s，但直接减少“正确完成任务的耗时”，尤其对重复长文档/稳定 system prompt 的 agent 工作流。
- 风险：32GB 内存当前空闲约 10.3GB；缓存 2.5–4GB 可能带来内存压力/换页。需测 `cache_n`、`prompt_ms`、总墙钟、系统内存。
- 何时无效：每次都是全新长文档、没有重复前缀；或缓存状态加载本身很慢。

#### C2. backend sampling

- 当前关闭；248K 词表的 CPU 采样可能占每 token 数毫秒，预期 2–8% 解码提升（估算）。
- 风险：experimental；采样器可能回退；固定 seed 不保证跨后端逐字一致；需质量抽查。
- 证伪：同输入 A/B，decode 提升 <3% 或采样器回退/质量差异，则不采纳。

#### C3. batch/ubatch

- 当前 `-b 512 -ub 128`；32K/56K prefill 约 860–924 t/s，56K TTFT 65s。
- 增大 `-ub`/`-b` 可能改善 prefill/TTFT，但对 decode 不应期待翻倍；需注意 64K 下的计算缓冲/显存。
- 证伪：TTFT 无 >5% 改善，或显存不够/速度下降。

#### C4. threads

- 仅在仍保留 CPU 层时有意义；完整卸载后 CPU 只做词嵌入/调度，预计收益很小。
- 当前 `-t 6 -tb 6`，CPU 16C/32T；若 Stage A 因显存只能到 `-ngl 65`，可试 8/12。
- 证伪：decode 提升 <3% 或不稳定。

### D. 外部草稿/其他引擎（只有 A+B 不足才评估）

- DFlash2/EAGLE3 等目标专用草稿：需要额外权重/工作区，当前 16GB 显存更紧；兼容性和质量需本机验证。DFlash2 的 Q4_K_M 约 1.14GB，仅权重就比 MTP 大很多；不应在 MTP 未测前先上。
- Vulkan/vLLM/其他引擎：CUDA 已正常工作；换引擎是独立工程，可能解决不了显存/功耗/上下文约束，不能假定更快。
- 更低量化/更小模型/购买硬件：违反第一阶段约束或不是首选；不列入本轮。

|---|---|---|---|---|---|

- 32K 默认、V=q4、更低量化：违反当前 64K/q8/权重量化约束，或质量风险未评估。

### 6.2 质量矩阵（与速度分开）

| 类别 | 题数（初筛） | 评分 | 采样 | 输出预算 |
|---|---:|---|---|---:|
| 多步逻辑/数学 | 20–25 | 标准答案精确匹配 | temp 0；随机题多 seed | ≥ 4096–8192 |
| 代码生成/修复 | 15 | 单元测试通过率 | temp 0 + 多 seed | ≥ 4096 |
| 中文取证/证据分析 | 12 | 固定 rubric：时间线/哈希/进程/网络/引用 | temp 0 + 3 次抽样 | ≥ 4096 |

| 结构化工具调用 | 10 | JSON schema/工具执行 | temp 0 | ≥ 2048 |

方法：
- 当前配置 vs 候选配置配对；同 prompt、同采样、同思考预算、同输出上限；随机化运行顺序减少热漂移。
- 随机性任务至少 3 次采样；报告正确率、失败类型（方法错/算术错/漏证据/幻觉/格式/截断/循环/超时），不只报一个总分。
- 不能只用模型自评；用标准答案、自动测试或明确 rubric。开放题由独立评分者按 rubric 打分。
- 记录“正确完成耗时”（TTFT + 到最终正确答案的时间）和“错误完成耗时”；不能只报成功的样本。
- 非劣性门槛（建议，需用户确认）：总体正确率下降不超过 5 个百分点；50 题中不增加超过 2 个失败；任何类别不出现塌陷；报告置信区间，承认 40–60 题无法证明“零退化”。
- 思考预算实验单独做：按请求 `reasoning_budget_tokens` 设 2048/4096/8192，输出上限必须 ≥ 预算 + 答案 + 余量；不与速度结论混合。

### 6.3 采纳/淘汰

采纳必须同时满足：
1. decode 均值提升 > 正常波动（建议 > max(5%, 2×基线标准差)）；TTFT 若作为目标，>5% 或 >2s。
2. 质量回归未发现明确退化；达到预设非劣性门槛；失败类型没有系统性恶化。
3. 64K 下连续 10 分钟稳定：无 OOM、无静默截断、无共享显存持续增长、温度/功耗在可控范围。
4. 若只在短上下文提升、56K 不提升，分别报告，不能宣称“64K 全场景达标”。

淘汰/暂不采纳：
- 提升在波动内、或只在单次跑分出现。
- 质量有明确退化、或失败类型向“漏证据/幻觉”集中。
- 64K 下不稳定、需要缩上下文/降 KV/降思考才能跑。
- MTP 接受率低、实际输出 token 数没有增加、或草稿开销抵消收益。

## 7. 达到 30 / 40 token/s 分别还缺什么

### 7.1 算术门槛

| 输入 | 当前 decode | 到 30 需要 | 到 40 需要 |
|---|---:|---:|---:|
| 短 | 27.65 | 1.085× | 1.447× |
| 12K | 26.00 | 1.154× | 1.538× |
| 32K | 25.13 | 1.194× | 1.592× |
| 56K | 22.57 | 1.329× | 1.772× |

这些是算术阈值，不是预测。

### 7.2 30 token/s 的条件

- **短/12K**：完整卸载只要带来约 8.5%/15.4% 的提升，就有可能到 30；按 CPU 层 5–10ms/token 的估算，这是现实的，但必须实测。若完整卸载只有 5%，短输入约 29.0，不够。
- **32K**：需要约 19.4%；完整卸载 + 少量缓存/采样优化可能达到，但不确定性较大。
- **56K**：需要约 32.9%；仅完整卸载（估 1.05–1.20×）不够，必须叠加 MTP 或显著降低注意力成本。MTP 若每步平均接受约 1.7–2.0 个 token，可能到 30；若接受率低，达不到。

### 7.3 40 token/s 的条件

- **短/12K**：需要 1.45–1.54×；几乎必须有 MTP，且接受率较高（每步平均约 2+ token），同时完整卸载。仅靠 backend sampling/ubatch 不够。
- **32K**：需要 1.59×；MTP 高接受率 + 完整卸载 + 功耗不触顶。
- **56K**：需要 1.77×；只有在 MTP 每步平均接受约 2.3–2.6 个 token、完整卸载、显存/功耗都过关时才可能。按当前 16GB/64K/q8/175W 约束，**不能承诺 40**；这是最可能失败的档位。
- 粗略敏感度（【估算】，不是预测）：
  - 若 MTP 每步接受期望 a 个 token（含 bonus），草稿成本按 3 次草稿、每次约为目标步的 0.10–0.15 计，speedup ≈ a / (1 + 0.30–0.45)。
  - a=1.5 → 1.03–1.15×；a=2.0 → 1.38–1.54×；a=2.5 → 1.72–1.92×；a=3.0 → 2.07–2.31×。
  - 所以 40 在短/12K 需要 a 约 1.9–2.2，32K 约 2.1–2.3，56K 约 2.3–2.6（取决于草稿成本），对应较高的逐位置接受率（约 0.75–0.85）。这是必须用实测接受率验证的，不是承诺。
- 若 MTP 逐位置接受率只有 0.5–0.6，按上述公式预计 speedup 约 1.3–1.6×：12K 约 33.8–41.6、56K 约 29.3–36.1；30 在 56K 可能刚好，40 在 12K 有希望、在 56K 仍不够。

### 7.4 “总时间”比 token/s 更重要的地方

| 输入 | TTFT | 512 token 解码@当前 | 总时间@当前 | 总时间@30 | 总时间@40 | 30/40 的总时间降幅 |
|---|---:|---:|---:|---:|---:|---:|
| 短 | 0.51s | 18.5s | 19.0s | 17.6s | 13.3s | 7% / 30% |
| 12K | 13.00s | 19.7s | 32.7s | 30.1s | 25.8s | 8% / 21% |
| 32K | 34.63s | 20.4s | 55.0s | 51.7s | 47.4s | 6% / 14% |
| 56K | 64.85s | 22.7s | 87.5s | 81.9s | 77.6s | 6% / 11% |

结论：
- 短/12K 的 decode 提升对总时间更有意义；56K 的瓶颈是 prefill/TTFT，decode 从 22.6 到 40 只省约 10s。
- 对 56K 任务，优先测 `-ub 256/512`、`--cache-ram`、稳定前缀；这些可能比追求 40 token/s 更快地减少“正确完成时间”。
- 但 prefill 优化不能违反“不静默截断、不删证据”；缓存只对重复前缀有效，不能替代首次完整处理。

### 7.5 可行性结论

在硬约束（64K、当前 IQ3-MIX、思考 2048、K/V q8_0、单请求、现有电脑）下：
- **当前配置不可能达到 30–40**：四档实测 22.57–27.65。
- **30 token/s**：短/12K 有现实希望（完整卸载 + 可能 MTP）；32K 较难；56K 需要 MTP 且接受率/显存过关。不能承诺全场景 30。
- **40 token/s**：短/12K 需要 MTP 高接受率；32K/56K 很可能达不到，尤其 56K。不能承诺。
- **如果 Stage A/B 实测失败**（OOM、接受率低、功耗触顶、质量退化），应明确报告“64K + q8 + 当前权重下达不到”，而不是继续堆参数或偷偷缩上下文。

## 8. 已测、未测与剩余不确定性

### 8.1 已测（可复核）

- 实际进程、命令行、计划任务、模型路径、引擎版本、CUDA 后端。
- GGUF 866 张量的类型/字节/块结构；官方 Qwen 配置交叉核对。
- 源码确认：`i_gpu_start`、输出层放置、MTP 张量跳过/加载、MTP context 单层 KV、speculative 采样/验证、per-request reasoning budget。
- 四档单请求基线（短/12K/32K/56K）×3；无前缀复用；cache_n=0；512 token；TTFT/decode/总时间。
- GPU 功耗/时钟/温度/利用率/显存遥测；llama-server 专用/共享显存恒定。
- 前缀复用 12K 对照（冷/热）。
- 数论题 2048/4096 预算探针；55K 长文唯一字段定位（128 截断版 + 256 通过版）。
- 日志无 OOM/truncated；长 prompt state 超过 `--cache-ram 512` 被跳过。

### 8.2 未测（明确）

- `-ngl all` / `-ngl 65` 的完整卸载速度与稳定性。
- MTP n_max=1/2/3 的启动、显存、接受率、速度、质量。
- MTP + 64K + 完整卸载组合是否真的能启动。
- backend sampling、ubatch/batch、threads、cache-ram 改动的效果。
- 10 分钟单一条件持续测试（当前只有约 7.4 分钟混合长文负载）。
- 有前缀复用的 56K 受控测试（仅做了 12K 冷/热）。
- 64K 满输入（受输出空间限制，未做）。
- 40–60 题质量回归、代码单元测试、中文多跳/冲突证据、工具调用。
- 外部草稿（DFlash2/EAGLE3）、Vulkan/vLLM 对比。
- 逐层 profiler / `load_tensors` 逐层日志；当前放置结论是源码 + 显存账目。
- GPU OC、Windows 图形调度、iGPU 分流（AMD 610M 当前未启用）。
- 多用户/并发吞吐（本轮明确不看）。

### 8.3 剩余不确定性（按影响排序）

1. **MTP 接受率与本机可用性**：最大未知；决定 40 是否可能。可能在 64K 下因显存无法启动。
2. **MTP 草稿 KV 类型（q8 vs F16）**：默认 F16 单层 256MiB，显式 q8 为 136MiB；q8 更省显存但可能降低草稿接受率，F16 更占显存但可能接受率更高。必须把“显存可行性”和“接受率”一起测，不能只按 q8 计算预算后就假定 F16 可跑。
3. **完整卸载的实际增益**：源码上确定会移除 2 个 CPU 块，但实际每 token 串行开销可能只有几毫秒；5–20% 是估算。
4. **MTP 图/工作区真实大小**：100–250MiB 是估算；可能更大，导致 A+B 放不下。
5. **功耗/温度上限**：长文已 161W 中位、79°C；MTP 叠加后可能触顶，实际加速比低于带宽估算。
6. **质量回归**：当前 2048 预算已在硬题上失败；更大预算/草稿/后端采样对质量的影响未测。
7. **长文总时间**：prefix 缓存/ubatch 的收益未测；它们可能比 decode 优化更重要。
8. **日志缺失**：没有逐层 `load_tensors` 输出；放置结论不是 profiler 直接观测，虽然显存账目高度吻合。

### 8.4 资料冲突

- 65W vs 175W：不同时间点的功耗策略不同；以当前 175W 为准，旧 65W 不作为当前状态。
- `file_type=13`/`Q3_K - Large` vs 实际张量混合：以 866 张量实读为准。
- 旧分析建议 32K 常规档 vs 当前 64K 硬约束：以当前约束为准，32K 不作为第一阶段方案。
- MTP “存在/支持” vs “本机跑通”：前者有源码/元数据证据，后者未测；不能混为一谈。

## 10. 最终结论与需要用户决定的事项

**当前事实**：
- 本机配置、模型、引擎、CUDA 后端、64K/q8/思考预算都已核实。
- 当前 decode 22.57–27.65 token/s，四档均低于 30；当前配置不达标。
- 瓶颈是显存余量、2 个 CPU 主干块、稠密权重带宽、长上下文注意力、以及 56K 的 prefill/TTFT；功耗 175W 已生效，不再是 65W 锁死。
- 完整卸载（+324.9MiB）是低成本第一步；MTP 是唯一有机会到 40 的模型内第二步，但 64K 下显存紧、接受率未知、从未在本机跑通。
- 前缀缓存已实测能把 12K 冷/热总时间从 16.9s 降到 4.8s；长文 56K 的状态缓存受 `--cache-ram 512` 限制，值得单独优化。
- 质量不能假定无退化：2048 预算在硬题上已经失败；任何提速方案必须做配对质量回归。

**不建议现在做的事**：
- 不要直接把 32K 当默认；不要改 V=q4、降量化、缩输出、提前结束思考来“达标”。
- 不要在没有实测的情况下宣布 MTP 会提速或 40 可达。
- 不要用单次跑分、合成接受率或多请求吞吐证明单请求提速。

**建议的下一步（需要用户批准维护窗口）**：
1. 先做 P1（释放其他 GPU 应用，不改配置）并记录可用显存。
2. 通过后做 P2（`-ngl all`，no MTP）四档 ×3；若 OOM，降级 `-ngl 65`。
3. P2 至少 >5% 且 64K 稳定，再做 P3（MTP n=1/2/3），记录接受率与显存。
4. 在胜出配置上做 10 分钟持续 + 40–60 题配对质量回归；不通过就回滚。
5. 同时独立做 C1（cache-ram/稳定前缀），它可能比 decode 优化更快降低长文总时间。

本轮**没有实施优化，也没有达到 30–40**；以上是调查、实测基线与可审查的实施方案。是否进入 Stage A，需要你确认维护窗口和可关闭的 GPU 应用。
